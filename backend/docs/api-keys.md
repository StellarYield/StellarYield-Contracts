# API Key Lifecycle Guide

This guide covers how API keys are created, stored, rotated, expired, deactivated for inactivity, and scoped to specific vaults.

## Storage & Hashing

API keys are **never stored in plaintext**. When a key is generated by `backend/src/scripts/generate-api-key.ts`:

- A 32-byte random hex token is prefixed with `sky_` (`sky_<64 hex chars>`).
- A 16-byte random hex salt is generated and stored in `api_keys.key_salt`.
- Only the salted SHA-256 digest (`SHA-256(salt || plaintext)`) is stored in `api_keys.key_hash`.
- During authentication (`backend/src/api/middleware/auth.ts`), the server re-derives the salted hash and compares it using `timingSafeEqual`. (Legacy unsalted SHA-256 hashes without `key_salt` are also supported for backwards compatibility.)

The plaintext key is printed once at creation or rotation and cannot be recovered afterwards.

## 1. Creation

Create a new API key using `npm run generate-key` (`tsx src/scripts/generate-api-key.ts`):

```bash
npm run generate-key -- --role admin --expires-in 90
```

Supported flags in `backend/src/scripts/generate-api-key.ts`:

| Flag | Default | Description |
| --- | --- | --- |
| `--role <admin\|readonly>` | `admin` | Key role (`admin` or `readonly`). |
| `--expires-in <days>` | `null` (no expiry) | Positive number of days until `expires_at`. |
| `--allowed-methods <list>` | `null` (all methods) | Comma-separated HTTP methods (`GET`, `HEAD`, `OPTIONS`, `POST`, `PUT`, `PATCH`, `DELETE`). |
| `--allowed-cidrs <list>` | `null` (all IPs) | Comma-separated IPv4 CIDR ranges permitted to use the key. |
| `--allowed-contract-ids <list>` | `null` (all vaults) | Comma-separated Stellar vault contract IDs (`C[A-Z2-7]{55}`). |

## 2. Rotation & Overlap

Rotate the newest active key for a label using `npm run rotate-api-key` (`tsx src/scripts/rotate-api-key.ts`):

```bash
npm run rotate-api-key -- --label my-admin-key --grace-days 7
```

How rotation works:

- Acquires a PostgreSQL advisory transaction lock per label (`api-key-label:<label>`).
- Requires at least one active, non-expired key with that `label`, and allows at most **2 active keys per label** (`MAX_ACTIVE_KEYS_PER_LABEL = 2`). If 2 active keys already exist, a second rotation fails until the grace period ends or one key is deleted.
- Inserts a new key under the same `label`, copying `role`, `expires_at`, `description`, `allowed_methods`, `allowed_cidrs`, `allowed_contract_ids`, and `rate_limit_override`.
- Sets the old key's `expires_at` to `LEAST(COALESCE(expires_at, 'infinity'), NOW() + graceDays)` (default `DEFAULT_GRACE_DAYS = 7` days; `--grace-days 0` expires it immediately). Both keys work during the overlap window so clients can roll over without downtime.

## 3. Expiry

- Keys created with `--expires-in` have an `expires_at` timestamp.
- **Response warning header:** Within `14` days (`KEY_EXPIRY_WARNING_DAYS`) of `expires_at`, authenticated responses include `X-API-Key-Expires-In` with the remaining lifetime in seconds.
- **Daily reminder job:** `logApiKeysExpiringSoon` (`backend/src/services/apiKeyExpiryReminder.ts`) logs a `warn` entry (`api_key_expiring_soon`) for active keys expiring within `7` days (`EXPIRY_REMINDER_WINDOW_DAYS`).
- **Once expired** (`expires_at <= NOW()`), requests are rejected with `401 Unauthorized`.

## 4. Inactivity Deactivation

Inactivity deactivation is controlled by `KEY_INACTIVITY_DAYS` (`backend/src/config.ts`). When `KEY_INACTIVITY_DAYS` is unset (the default), the sweep is a no-op.

When `KEY_INACTIVITY_DAYS` is configured, `deactivateInactiveApiKeys` (`backend/src/services/apiKeyInactivity.ts`) marks active keys as `active = FALSE` and sets `deactivated_at = NOW()` if:

```sql
COALESCE(last_used_at, created_at) < NOW() - make_interval(days => KEY_INACTIVITY_DAYS)
```

- Keys that were never used are measured from `created_at`.
- Deactivation is reversible by an operator (setting `active = TRUE` in `api_keys`); the sweep never deletes rows.
- Deactivated keys are rejected with `401 Unauthorized` and negative-cached in Redis (`revoked_key:<sha256>`) for `5` minutes (`REVOKED_KEY_CACHE_TTL_SECONDS`).

## 5. Per-Vault Restrictions

Keys can be restricted to specific vault contracts via `allowed_contract_ids` (passed at creation with `--allowed-contract-ids` and preserved on rotation):

- `NULL`: the key can access all vaults.
- Non-empty array of contract IDs: the key can only access the listed `C...` vault contracts.
- Empty array (`[]`): the key cannot access any vault contract.

`enforceApiKeyContractScope` (`backend/src/api/middleware/auth.ts`, mounted via `vaultsRouter.param("contractId", ...)` in `backend/src/api/routes/vaults.ts`) checks `isContractAllowedForKey(req.apiKey, contractId)` and returns `403 Forbidden` (`"API key is not permitted to access this vault"`) when a key accesses a vault outside its scope.

## 6. Key States Summary

| State | Condition | What It Allows |
| --- | --- | --- |
| **Active** | `active = TRUE` and (`expires_at IS NULL` or `expires_at > NOW()`) | Authenticates requests subject to `role`, `allowed_methods`, `allowed_cidrs`, `allowed_contract_ids`, and `rate_limit_override`. |
| **Expiring Soon** | Active, with `expires_at` within 14 days (header) / 7 days (reminder log) | Authenticates normally; responses include `X-API-Key-Expires-In` (≤14 days) and daily logs warn (`api_key_expiring_soon`, ≤7 days). |
| **Rotating (Grace Period)** | 2 active keys share the same `label` | Both old and new keys authenticate until the old key's `expires_at` lapses; further `rotate-api-key` runs for that label are blocked. |
| **Expired** | `expires_at <= NOW()` | Rejected with `401 Unauthorized`. |
| **Deactivated** | `active = FALSE` (e.g. inactivity sweep) | Rejected with `401 Unauthorized` (negative-cached 5 min in Redis); reversible by setting `active = TRUE`. |
| **Deleted / Revoked** | Row deleted via `DELETE /api/v1/admin/api-keys/:id` | Permanently rejected with `401 Unauthorized` (negative-cached 5 min in Redis). |
